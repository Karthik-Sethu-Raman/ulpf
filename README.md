# ULPF Prototype — Team Build Plan

**What this is:** A working prototype of the Universal Log Pre-processing
Framework (SIH PS 26156, NTRO, "Blockchain and Cybersecurity" theme). We
have 3 days. This is not the full production system from the idea PPT —
it's a narrow, real, end-to-end slice that proves the hard/differentiating
part actually works.

**The one sentence the whole team should have memorized:**
Perimeter device logs in unknown formats get a parser rule generated by a
local small language model (SLM); a human reviews and approves it; from
then on, every log of that format is parsed deterministically — no AI in
the hot path — and every normalized event stays traceable back to its raw
source.

## Repo structure

```
/schemas/schemas.py          <- canonical data contracts, DO NOT MODIFY casually
/testdata/fixtures/          <- example JSON instances of every schema type
/testdata/raw_logs_*.txt     <- mock raw logs in 3 formats (CEF, syslog, JSON)
/ingestion/                  <- P3's module
/parser_engine/               <- P2's module
/onboarding/                    <- P1's module (SLM rule generation)
/review_ui/                      <- P4's module (Streamlit)
/drift_monitor/                    <- P5's module
/testdata/integration_runner.py     <- P6's module
/docs/ROLE_P*.md                       <- individual role briefs, one per person
app.py                                    <- final integration entrypoint, built day 3
```

## Roles

| Person | Module | Depends on (at final integration only) |
|---|---|---|
| P1 | Onboarding engine (SLM) + integration lead | P3's raw events |
| P2 | Format fingerprinting + deterministic parser engine | P1's rules |
| P3 | Ingestion + raw storage + traceability + rule validation | nothing upstream |
| P4 | Review-gate UI + normalized event browser (Streamlit) | P1's rules, P3's validation |
| P5 | Drift monitor + simulated response | P2's normalized events |
| P6 | Test data + integration test runner | everyone (day 3 only) |

**Nobody is blocked on day 1-2.** Every module is built and tested against
the fixture files in `/testdata/fixtures/` — hand-written examples matching
the exact schema. Real data only flows between modules at final integration
on day 3.

## Timeline

**Day 1 — Build in isolation**
Everyone reads `schemas.py` + their own role file. Build your module against
the fixtures. By end of day: your module runs standalone and passes the
test assertions in your role file.

**Day 2 — First real vertical slice (CEF only)**
P1 + P2 connect for real: P1's generated rule (not a fixture) gets fed into
P2's parser engine, on the CEF sample logs. P3's ingestion/storage runs for
real underneath both. Get ONE format working truly end-to-end. This is the
checkpoint — if it's not working by end of day 2, cut scope, don't push on.

**Day 3 — Breadth + integration + demo**
Add syslog and JSON formats through the same real pipeline. P6 + P1 wire
everything into `app.py`. P5's drift monitor runs against real normalized
event output. Freeze features by early evening; record final demo footage
using the real system if time allows.

## Ground rules

- Import types from `schemas.py`. Never redefine them locally.
- Never silently drop a field that doesn't map to OCSF — put it in
  `unmapped_fields`.
- If you think the schema needs a new field, say so in the team chat before
  changing it. A silent schema change breaks everyone else's module.
- Keep Kafka, Postgres, and real Syslog network listeners OUT of scope for
  3 days — SQLite, local files, and a plain Python function pipeline are
  enough to prove the concept. State the production versions in the
  architecture doc, don't build them now.
